## 2. 接口验证（全部通过）

服务器：`genie.start_server(host="127.0.0.1", port=8000, workers=1)`，启动约数秒内端口就绪。

`/openapi.json` 确认存在 6 个接口：

- `POST /load_character`
- `POST /set_reference_audio`
- `POST /tts`
- `POST /unload_character`
- `POST /stop`
- `POST /clear_reference_audio_cache`

真实链路使用已有 ONNX 角色 **mika（日文）** 跑通：

```text
POST /load_character        -> 200  {"status":"success","message":"Character 'mika' loaded."}
POST /set_reference_audio   -> 200  {"status":"success","message":"Reference audio for 'mika' set."}
POST /tts                   -> 200  Content-Type: audio/wav
```

错误路径：

- 未加载角色的 `/tts` → 404 `Character not found or reference audio not set.`
- `.mp3` 参考音频 → 400 `Audio format '.mp3' is not supported. Supported formats: {'.aif', '.ogg', '.wav', '.aiff', '.flac'}`

## 3. `/tts` 音频格式（关键结论）

**实测 `/tts` 返回的是裸 PCM，不是带 WAV 头的完整 WAV 流。**

- 文件头无 `RIFF`/`WAVE` 标记（实测文件 `logs/phase0_mika_tts.wav`，445440 字节）。
- 源码确认：`TTSPlayer.sample_rate=32000`、`channels=1`、`bytes_per_sample=2`（16bit），
  `_preprocess_for_playback()` 输出 `int16` 裸采样字节；只有传入 `save_path` 时服务端才用 `wave` 模块写 WAV 头。
- 实测数据按 32000 Hz 单声道 16bit 换算：222720 帧 ≈ 6.96 秒，与文本长度吻合。
- HTTP 头 `Content-Type: audio/wav` 具有误导性，中间件不能仅凭该头判断格式。

对后续阶段的影响：

- 阶段 5（流式播放）必须调整：`ffplay -i -` 需改为 `ffplay -f s16le -ar 32000 -ac 1 -`，
  或在中间件侧为裸 PCM 补 WAV 头。
- 若要服务端直接产出 WAV 文件，可给 `/tts` 传 `save_path`（服务端写盘，不推荐中间件依赖本地盘）。

## 4. 健康检查（无内置接口）

`/openapi.json` 中无 health/ping/status 类接口。

建议替代方案：

- 进程级存活探测：TCP 连接 `127.0.0.1:<port>` 即可（启动等待用）。
- 角色就绪探测：由于 `/tts` 在“角色已加载 + 参考音频已设置”前固定返回 404，可将其作为轻量探测；
  更可靠的做法是中间件在预加载完成后自行标记 ready，再开放 7788 端口。

## 5. 其他发现与风险记录

1. **`/load_character` 的 200 不一定代表加载成功**：`model_manager.load_character()` 内部捕获异常并返回
   `False`，但服务端接口不检查返回值，仍返回 `{"status":"success"}`。阶段 4 预加载逻辑不能只依赖
   HTTP 200，需通过后续 `/tts` 探测或检查日志确认角色可用。
2. **角色名大小写**：`model_manager` 内部统一转小写，但 `/set_reference_audio` 的注册表按原样区分大小写；
   阶段 2/3 应统一使用小写 `character_name`，避免大小写不一致导致 404。
3. **已有可复用 ONNX 模型**：`F:\AiSound\Genie-TTS GUI\CharacterModels\v2ProPlus\`
   下已有 feibi（zh）、mika（jp）、thirtyseven（en）三个转换好的 V2ProPlus 角色及参考音频，
   证明 V2ProPlus ONNX 转换产物可被当前 genie-tts 2.0.2 正常加载。阶段 1 仍需为项目的
   ema / hiro / MyGO / 诗歌剧 / sherry 执行转换。
4. **参考音频格式**：支持 `.wav .flac .ogg .aiff .aif`，不支持 `.mp3`；现有角色音频若含 mp3 需先转换。
5. **内存占用**：mika 单角色加载 + 一次短句合成在 CPU 上约 20 秒内完成（含模型加载）；
   多角色并发预加载的内存占用留待阶段 4/7 实测（`Max_Cached_Character_Models` 环境变量可调缓存容量，默认 3）。
6. **端口**：阶段 0 使用 8000（教程默认）。计划阶段 2 将 `baseUrl` 配置为 Genie 服务器地址，端口可后续统一。

## 6. GPU 合成验证补充（2026-08-06）

**环境变更**

- 合成推理由 onnxruntime 执行（非 torch），GPU 版需安装 `onnxruntime-gpu`。
  GPU 版没有 1.22.1，已安装 **onnxruntime-gpu 1.22.0**（genie-tts 锁定的 1.22.1 仅 CPU 版存在）。
- 通过 `onnxruntime-gpu[cuda,cudnn]` 安装 nvidia 官方运行时：
  CUDA 12.9（cudart/cublas/cufft/curand/nvrtc/nvjitlink）+ cuDNN 9.24，
  安装在 `.venv-genie\Lib\site-packages\nvidia\*\bin`。
- **关键坑**：onnxruntime 的 `_ld_preload.py` 在 Windows 上是空实现，不会自动加载
  nvidia 包中的 DLL。必须在 `import genie_tts / onnxruntime` 之前把所有
  `nvidia\*\bin` 加入 DLL 搜索路径（`os.add_dll_directory` + PATH）。
  否则 `onnxruntime_providers_cuda.dll` 报 `cublasLt64_12.dll is missing`，
  且 onnxruntime 会静默回退 CPU——只看 `get_available_providers()` 会误判。

**验证结果（真实 GPU 运行）**

- 验证脚本用最小 ONNX 模型实测 `CUDAExecutionProvider` 会话创建成功，不再仅看 provider 列表。
- 运行期间 `nvidia-smi` 采样确认：服务器 Python 进程出现在 compute-apps 列表；
  显存占用从约 2.4GB 升至峰值约 5.4GB（模型约 3GB）；GPU 利用率峰值 50%+。
- mika 日文短句（5.80 秒音频）合成成功。

**WAV 头**

- `/tts` 返回裸 PCM（16bit、单声道、32000Hz），验证脚本现在在客户端用 `wave` 模块
  补 WAV 头后落盘，`logs\phase0_mika_tts.wav` 可直接双击播放。
- 阶段 5 播放链路仍按“裸 PCM + 补头”或 `ffplay -f s16le -ar 32000 -ac 1 -` 设计。

**风险提示（影响阶段 4/7）**

- RTX 2060 只有 6GB 显存，且本机常驻程序（壁纸引擎、Chrome、OBS、旧 GPT-SoVITS 等）
  已占用约 2.4GB。单角色 GPU 加载峰值约 5.4GB，已非常接近上限。
- 多角色同时 GPU 预加载大概率显存不足，阶段 4 需要评估：
  仅缓存 1 个角色（`Max_Cached_Character_Models=1`）+ 按需加载/卸载，
  或 GPU/CPU 混合策略，而不是“全部角色 GPU 预加载”。
