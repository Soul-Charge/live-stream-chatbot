# 弹幕数据库构建计划（Danmaku DB Plan）

> 目标：把中间件收到的每一条弹幕（含被过滤/拒绝的）落到本地数据库，为后续功能扩展建立统一数据底座。
> 本计划只做**规划与设计**，代码实施按阶段拆分，先采集、后查询、再与 TTS 缓存联动。

## 1. 背景与目标

当前 `live-stream-chatbot` 只负责“接收弹幕 → 清洗 → TTS → 播放”，弹幕数据用完即弃。缺少本地数据库导致以下能力无法实现：

1. **高频弹幕预生成 TTS 缓存**：统计一段时间内重复次数超过阈值的文本，提前合成音频文件；之后相同弹幕直接播放缓存，首音延迟接近 0，且重启后仍可命中。
2. **直播间观众图谱**：谁在什么时间发言、发言频次、与其他观众的时间共现关系。
3. **历史发言查询**：按时间、用户、文本、角色检索弹幕。
4. **词云 / 热词分析**：中文/日文混合弹幕的分词与词频统计。
5. **数据回放与导出**：复盘直播效果、生成语料集、调试角色匹配和屏蔽规则。

### 实施状态（2026-08-21 更新）

| 阶段 | 状态 | 说明 |
| --- | --- | --- |
| 阶段 1 数据采集 | 已实现（Windows 运行时需先 `npm rebuild better-sqlite3`） | `src/db/*`、`index.js` 全量入库、TTS 状态跟踪、拒绝记录 |
| 阶段 2 查询与分析 | 基本实现 | `/db/danmaku`、`/db/hot`、`/db/users`、`/db/sessions`、保留清理、`npm run db:backup` |
| 阶段 3 热句预生成文件缓存 | 规划细化，未实施 | 已新增 `vibe-coding-reference/高频弹幕缓存机制计划.md`；包含磁盘缓存、模型指纹、低优先级预生成、缓存 API/WebUI |
| 阶段 4 观众图谱 / 词云 / 回放 | 未实施 | 依赖分词与共现分析设计 |

设计原则：

- **采集完整**：保存原始文本、清洗文本、角色匹配结果、TTS 状态；被屏蔽/过滤的也入库。
- **不阻塞主链路**：数据库写入失败只能降级记录日志，不能影响 202 响应、TTS 与播放。
- **本地优先**：单机、单文件、零运维；不引入独立数据库服务。
- **可扩展**：核心表稳定，扩展信息进 JSON 字段；分析类结果可重建，不污染原始表。
- **可治理**：支持保留期、备份、迁移和隐私清理。

## 2. 技术选型

### 2.1 主存储：SQLite

| 评估项 | 结论 |
| --- | --- |
| 数据库 | SQLite 3.34+（建议跟随本机最新稳定版） |
| Node 驱动 | `better-sqlite3`（v1 推荐） |
| 备选驱动 | `node:sqlite`（Node 22.5+，需升级 engines）；`sqlite3` 异步包（原生依赖更老） |
| 文件位置 | `data/danmaku.sqlite3`（加入 `.gitignore`） |
| 运行模式 | `journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`、`foreign_keys=ON` |
| 理由 | 本地单进程、弹幕写入量低（通常 < 10~30 条/秒），SQLite 足够；WAL 支持读写并发，文件单一易备份 |

选择 `better-sqlite3` 的理由：

- 同步 API 简单，单条 INSERT 在 WAL + prepared statement 下通常 < 1ms，不会显著阻塞 HTTP 主链路。
- 性能足够支撑统计查询；复杂分析可在空闲时或独立进程中执行。
- 若安装/编译困难，降级方案为 `node:sqlite`（升级项目 `engines.node >= 22.5`）或 `sqlite3` 异步驱动。

### 2.2 分析层：暂不引入，必要时补 DuckDB

- 词云、观众图谱等重分析可以在空闲时间用 SQL 直接完成。
- 若未来弹幕量达到百万级且需要列式聚合，可导出/附加为 DuckDB 文件，不替代 SQLite 主库。

### 2.3 中文/日文分词

| 阶段 | 方案 |
| --- | --- |
| v1 | 不依赖分词：高频缓存按“完全相同的清洗后文本”分组；中文子串查询用 SQLite FTS5 `trigram` tokenizer |
| v2 | 引入分词器生成 `tokens` 列，中文用 `@node-rs/jieba`，日文用 `kuromoji.js` 或 `sudachi.rs` 的 Node 绑定；词云/观众兴趣从 tokens 统计 |

## 3. 数据模型（Schema v1）

统一时间存储：**UTC epoch 毫秒整数**，展示层再转本地时区。所有扩展字段使用 `metadata_json`，避免频繁改表。

### 3.1 表结构

```sql
PRAGMA user_version = 1;

-- 直播场次：中间件启动并收到第一条弹幕时创建，正常关闭时结束
CREATE TABLE live_sessions (
  id            INTEGER PRIMARY KEY,
  started_at_ms INTEGER NOT NULL,
  ended_at_ms   INTEGER,
  room_id       TEXT,
  title         TEXT,
  metadata_json TEXT NOT NULL DEFAULT '{}'
);

-- 发言用户：为观众图谱提供用户维度
CREATE TABLE users (
  id             INTEGER PRIMARY KEY,
  user_key       TEXT NOT NULL UNIQUE,  -- 有 uid 时为 'uid:<uid>'，否则 'name:<username>'
  uid            TEXT,
  username       TEXT NOT NULL,
  first_seen_at_ms INTEGER NOT NULL,
  last_seen_at_ms  INTEGER NOT NULL,
  message_count  INTEGER NOT NULL DEFAULT 0,
  metadata_json  TEXT NOT NULL DEFAULT '{}'
);

-- 弹幕主表：每收到一条写入一行，包括被过滤/拒绝的
CREATE TABLE danmaku (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  session_id     INTEGER REFERENCES live_sessions(id),
  received_at_ms INTEGER NOT NULL,
  user_id        INTEGER NOT NULL REFERENCES users(id),
  uid            TEXT,
  username       TEXT NOT NULL,
  raw_text       TEXT NOT NULL,
  clean_text     TEXT NOT NULL,
  speech_text    TEXT NOT NULL,
  text_len       INTEGER NOT NULL,
  speech_hash    TEXT NOT NULL,          -- sha1(speech_text) 十六进制
  role_key       TEXT NOT NULL,
  role_comment   TEXT,
  accepted       INTEGER NOT NULL DEFAULT 1,  -- 0=被拒绝/屏蔽
  reject_reason  TEXT,
  tts_status     TEXT NOT NULL DEFAULT 'accepted'
                 CHECK (tts_status IN ('accepted','queued','synthesizing','played','cache_hit','disk_cache_hit','skipped','error')),
  used_cache     INTEGER NOT NULL DEFAULT 0,  -- 本条播放是否命中了缓存
  tts_error      TEXT,
  cache_key      TEXT,
  metadata_json  TEXT NOT NULL DEFAULT '{}'
);

-- TTS 音频文件缓存：磁盘缓存，重启不丢；也服务高频预生成
CREATE TABLE tts_audio_cache (
  cache_key        TEXT PRIMARY KEY,      -- '<role_key>\n<speech_text>'
  role_key         TEXT NOT NULL,
  speech_text      TEXT NOT NULL,
  speech_hash      TEXT NOT NULL,
  file_path        TEXT NOT NULL,
  media_type       TEXT NOT NULL DEFAULT 'wav',
  duration_ms      INTEGER,
  size_bytes       INTEGER NOT NULL,
  first_created_at_ms INTEGER NOT NULL,
  last_hit_at_ms   INTEGER,
  hit_count        INTEGER NOT NULL DEFAULT 0,
  source           TEXT NOT NULL DEFAULT 'request'
                   CHECK (source IN ('request','hot_pregen','manual')),
  metadata_json    TEXT NOT NULL DEFAULT '{}',
  UNIQUE (role_key, speech_hash)
);

-- 热句预生成任务：可观测、可重试，避免重复劳动
CREATE TABLE hot_phrase_jobs (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  window_start_ms INTEGER NOT NULL,
  window_end_ms   INTEGER NOT NULL,
  role_key       TEXT NOT NULL,
  speech_text    TEXT NOT NULL,
  speech_hash    TEXT NOT NULL,
  count          INTEGER NOT NULL,
  status         TEXT NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','running','done','skipped','error')),
  cache_key      TEXT,
  error          TEXT,
  created_at_ms  INTEGER NOT NULL,
  completed_at_ms INTEGER
);

-- 索引：按计划中的主要查询路径建立
CREATE INDEX idx_sessions_started   ON live_sessions(started_at_ms);
CREATE INDEX idx_danmaku_time       ON danmaku(received_at_ms);
CREATE INDEX idx_danmaku_user_time  ON danmaku(user_id, received_at_ms);
CREATE INDEX idx_danmaku_role_time  ON danmaku(role_key, received_at_ms);
CREATE INDEX idx_danmaku_status     ON danmaku(tts_status, received_at_ms);
CREATE INDEX idx_danmaku_hot        ON danmaku(role_key, speech_hash, received_at_ms);
CREATE INDEX idx_hot_jobs_window    ON hot_phrase_jobs(window_end_ms, status);
CREATE INDEX idx_cache_role_hash    ON tts_audio_cache(role_key, speech_hash);
```

### 3.2 数据写入规则

| 字段 | 规则 |
| --- | --- |
| `raw_text` | 请求原文本，不做任何清洗；角色识别也基于它 |
| `clean_text` | `cleanText(..., applyReplacements=false)` 结果 |
| `speech_text` | `cleanText(..., applyReplacements=true)` 结果，即最终送 TTS 文本 |
| `role_key` | `matchRole` 返回的角色键 |
| `tts_status` | 随 TTS 队列生命周期更新：`accepted → queued → synthesizing → played/cache_hit/disk_cache_hit/error`；`accepted=0` 时固定为 `skipped`；`used_cache=1` 表示本次播放命中缓存 |
| `speech_hash` | `sha1(role_key + '\n' + speech_text)` 或单独 `sha1(speech_text)`，v1 统一为 `sha1(speech_text)`，查询时与 `role_key` 组合；v2 缓存命中还结合 `model_key` |

### 3.3 高频弹幕统计 SQL（v1 直接可用）

```sql
SELECT
  role_key,
  speech_text,
  speech_hash,
  COUNT(*) AS cnt,
  MIN(received_at_ms) AS first_seen,
  MAX(received_at_ms) AS last_seen
FROM danmaku
WHERE received_at_ms >= :window_start
  AND received_at_ms <  :window_end
  AND accepted = 1
  AND text_len BETWEEN :min_len AND :max_len
GROUP BY role_key, speech_hash
HAVING COUNT(*) >= :min_count
ORDER BY cnt DESC, last_seen DESC
LIMIT :top_n;
```

### 3.4 Schema v2：高频弹幕缓存表（规划中）

根据最新需求，高频弹幕缓存使用独立表 `hot_danmaku`，只保存满足高频条件的内容与音频地址；音频地址初始为空，由 WebUI 触发生成后回填。

```sql
CREATE TABLE hot_danmaku (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  role_key          TEXT NOT NULL,
  role_comment      TEXT,                   -- config.roles[role_key].comment，用于目录分类
  model_key         TEXT NOT NULL DEFAULT '',
  speech_text       TEXT NOT NULL,
  speech_hash       TEXT NOT NULL,          -- sha1(speech_text)
  window_hours      INTEGER NOT NULL,
  min_count         INTEGER NOT NULL,
  occurrences       INTEGER NOT NULL,
  first_seen_at_ms  INTEGER NOT NULL,
  last_seen_at_ms   INTEGER NOT NULL,
  status            TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending','generating','ready','error')),
  audio_path        TEXT,                   -- 初始为 NULL/空，生成后写入
  error             TEXT,
  created_at_ms     INTEGER NOT NULL,
  updated_at_ms     INTEGER NOT NULL,
  metadata_json     TEXT NOT NULL DEFAULT '{}',
  UNIQUE (role_key, model_key, speech_hash, window_hours, min_count)
);

CREATE INDEX idx_hot_danmaku_time
  ON hot_danmaku(last_seen_at_ms DESC);

CREATE INDEX idx_hot_danmaku_status
  ON hot_danmaku(status);
```

说明：

- `audio_path` 允许为空，表示尚未生成音频。
- `status` 记录生成状态：`pending` / `generating` / `ready` / `error`。
- `model_key` 用于区分同一角色更换模型后的音频。
- 原有 `tts_audio_cache` / `hot_phrase_jobs` 可作为可选的运行时缓存/任务审计表，不再作为高频弹幕主表。

> 详细设计见 `vibe-coding-reference/高频弹幕缓存机制计划.md`。


## 4. 系统设计

### 4.1 新增模块

```

  connection.js         -- better-sqlite3 单例、WAL、busy_timeout

  DanmakuWriter.js      -- 可选：写队列、批量提交、降级策略
  danmakuApi.js         -- HTTP 路由：查询 + 高频弹幕扫描/生成

  hotPhraseService.js   -- 高频统计 + 预生成任务调度
src/cache/
  TtsFileCache.js       -- 磁盘音频缓存读写（可与现有内存 LRU 共存）
```

### 4.2 写入链路（阶段 1 先只采集）

1. `parseRequest` 完成后，无论最终是否被 TTS 处理，都构造 `DanmakuRecord`。
2. 写入数据库：
   - v1 采用 prepared statement 同步 INSERT；WAL + `synchronous=NORMAL` 下单次写入目标 < 1ms。
   - 若压测 p99 超过 2ms，切换为 `DanmakuWriter` 内存队列：攒批 50~100 条或 200ms flush 一次。
3. 发送 202 响应不等待数据库写入成功；失败仅记录 `[db]` 错误日志并丢弃当前缓存，不让弹幕主链路中断。
4. TTS 异步结果回调更新同一行的 `tts_status` / `tts_error` / `cache_key`：
   - `.then(stream => player.enqueue(stream))` 时标记 `queued`；
   - 播放完成/失败后标记 `played` / `error`；
   - 命中缓存时标记 `cache_hit` / `disk_cache_hit`。
5. 被 `RequestError` 拒绝的弹幕同样入库：`accepted=0`、`tts_status='skipped'`、`reject_reason` 记录原因，用于后续调优屏蔽词。

### 4.3 查询 API 与高频弹幕 API（仅监听 127.0.0.1）

| `GET /db/sessions` | 直播场次列表 |
| `GET /db/cache` | 磁盘缓存条目列表（阶段 3 新增） |
| `GET /db/cache/stats` | 缓存汇总：条目数、字节数、命中数、来源分布（阶段 3 新增） |
| `GET /db/hot-jobs` | 热句预生成任务列表（阶段 3 新增） |
| `GET /db/hot-danmaku` | 高频弹幕列表（阶段 3 新增） |

### 4.4 高频弹幕缓存（阶段 3，按最新需求）

详细设计见 `vibe-coding-reference/高频弹幕缓存机制计划.md`。核心流程如下：

1. **可配置高频判定**：
   - 支持多条规则，例如 `24h + 出现 10 次`、`1h + 出现 5 次`。
   - 定时或手动扫描 `danmaku`，把满足条件的内容写入 `hot_danmaku`。
2. **只存高频内容与音频地址**：
   - `hot_danmaku` 只保存高频弹幕文本、角色、模型、统计窗口/次数、状态和 `audio_path`。
   - `audio_path` 初始为空；未生成前不占音频存储。
3. **WebUI 触发生成/重新生成**：
   - 用户在 WebUI 点击“生成”或“重新生成”。
   - 后端调用 TTS 合成，成功后把音频文件写入 `audioDir`（目录使用 `role_comment` 分类），并回填 `audio_path`、`status='ready'`。
   - 每条记录独立生成，互不影响。
4. **试听与波形**：
   - WebUI 提供播放器和 Canvas 波形图，方便检查合成效果。
5. **运行时命中（核心）**：
   - 中间件每次收到弹幕后查询 `hot_danmaku`。
   - 如果匹配到已生成音频（`audio_path` 非空且文件存在），直接播放该音频，不再实时合成。
6. **模型隔离**：
   - `model_key`（`gpt_path + '\n' + sovits_path`）参与唯一约束，避免同一角色更换模型后命中旧音色。
7. **低优先级与限流**：
   - 生成任务走低优先级队列；若实时 TTS 繁忙或配置 `skipWhileBusy=true`，则顺延。
8. **可观测**：
   - 新增 `/db/hot-danmaku` 系列接口，供 WebUI 查看、扫描、生成和试听。

### 4.5 与现有 `tts.cache` 的关系（A4 → A5 取代）

| 缓存 | A4（过渡，默认关闭） | A5（目标方案） |
| --- | --- | --- |
| 形态 | 进程内内存 LRU | SQLite 索引 + WAV 文件 |
| 生命周期 | 重启丢失 | 重启保留 |
| 内容来源 | 请求时顺带缓存 | 请求缓存 + 热句预生成 |
| 命中路径 | 内存直接命中 | `tts_audio_cache` 查询 + `createReadStream` |
| 内存占用 | 默认关闭；临时开启上限 4 条 × 4MB | Node 只持有流缓冲；文件在磁盘 |

结论：**A5 稳定后完全取代 A4**，不再保留进程内音频 Buffer。实施顺序：先落地 A5 文件缓存，再跑热句任务预热；过渡期 A4 默认关闭（`tts.cache.enabled=false`），确需一级缓存时只允许显式开启极小容量（如 4 条 / 4MB），并在 A5 验收后从 `TTSEngine` 移除内存 LRU 代码。

配置热重载规则：

- `database.enabled`、`path` 改动需重启生效（连接已建立）。
- `retentionDays`、`hotPhrase.*`、`tts.cache.disk.*` 可热更新。
- 关闭 `database.enabled` 时保留文件，只停止写入。

## 6. 部署与实施阶段

### 阶段 1：数据采集（核心先行）

| 工作项 | 内容 | 验收标准 |
| --- | --- | --- |
| 依赖与连接 | 引入 `better-sqlite3`，新增 `src/db/*`，启动时执行 migration | `npm run check` 通过；首次启动自动建库。Windows 下如果日志出现 `not a valid Win32 application`，先执行 `npm rebuild better-sqlite3` |
| 全量入库 | 在 `index.js` 请求处理中记录全部弹幕与拒绝原因 | 模拟 100 条弹幕，入库 100 条；被屏蔽词拦截的也有记录 |
| TTS 状态跟踪 | 更新 `tts_status` 生命周期 | 查询单条弹幕可见 `accepted → queued → played` |

## 7. 运维与风险

### 7.1 备份

- **不在直播中直接复制主库文件**：WAL 未 checkpoint 时文件复制可能丢最近事务。
- 推荐用 SQLite backup API 或脚本执行：
  - Node：better-sqlite3 的 `db.backup(dest)`；
  - CLI：`sqlite3 data/danmaku.sqlite3 ".backup data/backup/danmaku-YYYYMMDD.sqlite3"`。
- 建议每天直播结束后备份一次；保留最近 7 份。

### 7.2 保留与清理

- 默认 `retentionDays=90`；清理 SQL 按 `received_at_ms < cutoff` 分批删除（每批 1000 行），避免长事务。
- 删除弹幕时同步删除其 FTS 影子行（阶段 2 引入 FTS 后）。
- 音频缓存淘汰与弹幕保留期解耦：热句音频可保留更久。

### 7.3 风险清单

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 原生模块 `better-sqlite3` 在 Windows 安装失败 | 无法建库 | 备选 `node:sqlite`（Node 22.5+）或 `sqlite3`；计划阶段 1 先验证安装 |
| WSL/Linux 与 Windows 共用同一 `node_modules` | Windows Node 加载 WSL 编译的 `better_sqlite3.node` 报 `not a valid Win32 application` | 当前代码会降级为不采集；在 Windows PowerShell 执行 `npm rebuild better-sqlite3` 或删除 `node_modules` 后重新 `npm install` |
| 同步 INSERT 阻塞事件循环 | 弹幕响应变慢 | 单次 WAL 写入目标 <1ms；超阈值切批量队列或 worker |
| 数据库与游戏/直播争抢磁盘 IO | 游戏卡顿 | WAL + 批量写入；必要时把 `data/` 放到非游戏盘 |
| 数据库无限增长 | 磁盘占满 | 保留期分批删除 + 容量监控 + `/db/health` 告警日志 |
| 隐私泄露 | 本地库含用户名/发言 | 仅监听 127.0.0.1；可选 `readToken`；默认不入库客户端 IP |
| 热句预生成与实时弹幕抢 GPU | 直播延迟上升 | 单轮限 3~5 条、队列忙则顺延；只预生成高置信热句 |
| 缓存文件损坏/不完整 | 播放失败或卡顿 | 写入用临时文件 + rename；读取前校验文件存在与大小；损坏则删除并重新合成 |
| 模型切换后命中旧音色 | 音色不对 | 缓存绑定 `model_key`；模型变化自动视为未命中 |
| 中文/日文分词不准 | 词云质量差 | 阶段 4 再引入；v1 用整句精确重复统计，不依赖分词 |
| 时间戳/时区混乱 | 统计窗口错误 | 全库统一 UTC epoch ms，展示层转换 |

### 7.4 容量估算

- 单条弹幕记录约 0.5~1.5KB（含索引约 1~3KB）。
- 一场 8 小时直播 1 万条弹幕约 10~30MB。
- 100 万条弹幕约 1~3GB，SQLite 仍可接受；超过百万后可启用按月分表或冷数据导出。
- 单条 TTS 音频 200~350KB；512MB 文件缓存可容纳约 1500~2500 条热句。

## 8. 与 TTS 优化计划的联动

- 本文档阶段 3 即 `vibe-coding-reference/TTS性能优化计划.md` 中的 **A5 高频弹幕预生成文件缓存**，详细设计见 `vibe-coding-reference/高频弹幕缓存机制计划.md`。
- A5 落地并验收后**完全取代 A4 内存 LRU**：命中路径统一走 `tts_audio_cache` + 磁盘文件，Node 进程不再缓存整段 WAV，降低内存占用。
- 数据库先落成后，缓存命中率、缓存字节数、热句排行榜都直接由 `danmaku` / `tts_audio_cache` 表查询，形成可量化优化闭环。
