# 高频弹幕缓存机制计划（Hot Danmaku Audio Cache Plan）

> 目标：按可配置的时间窗口和出现次数，自动识别高频弹幕；数据库只保存高频弹幕内容与对应音频地址（初始为空）；在 WebUI 中选择生成/重新生成音频，并提供带简易播放器和波形图的试听界面。
> 本文档是 `弹幕数据库构建计划.md` 阶段 3 的细化设计，也是 WebUI 中“高频弹幕/音频试听”页面的需求来源。

## 1. 背景与现状

### 1.1 当前语音合成链路

```
弹幕姬 POST /tts
  → parseRequest / matchRole
  → 入库 danmaku
  → TTSEngine.enqueue(speechText, role, roleName)
  → 请求 GPT-SoVITS 合成
  → 音频流交给播放器
```

目前没有可用的高频弹幕缓存：A4 内存 LRU 默认关闭，`tts_audio_cache` / `hot_phrase_jobs` 表已建但未接入业务。

### 1.2 新需求要点

1. **可配置高频判定**：例如“24 小时内出现 10 次”或“1 小时内出现 5 次”，满足条件才记录为高频弹幕。
2. **只存高频内容与音频地址**：数据库不保存普通弹幕的音频缓存，只保存高频弹幕文本和对应音频文件地址；音频地址初始为空。
3. **WebUI 触发生成**：在高频弹幕列表中选择“生成”，后端自动合成音频并回填地址。
4. **试听与波形**：界面类似 GPT-SoVITS 音频处理页，提供简易播放器和简易波形图。
5. **单独重新生成**：每条音频有独立“重新生成”按钮，结果不理想可随时重新合成。

## 2. 目标与非目标

### 2.1 目标

- 按配置自动扫描 `danmaku` 表，识别高频弹幕并写入独立的高频弹幕表。
- 高频弹幕表字段：内容、角色、模型、统计窗口/次数、音频路径（可空）、状态。
- WebUI 支持：
  - 查看高频弹幕列表
  - 点击“生成”合成音频并回填路径
  - 点击“重新生成”覆盖音频
  - 点击“试听”打开播放器 + 波形图
- 生成后的音频可在后续相同弹幕播放时直接命中（作为可选的运行时缓存）。

### 2.2 非目标

- 不做普通弹幕的全量音频缓存（除非后续需要）。
- 不做语义相似去重，只做精确文本匹配。
- 不做分布式/多机共享。
- 不改变 GPT-SoVITS 音色与合成参数。

## 3. 总体设计

### 3.1 高频判定规则

使用可配置的规则列表，例如：

```jsonc
{
  "hotPhrase": {
    "enabled": true,
    "rules": [
      { "windowHours": 24, "minCount": 10 },
      { "windowHours": 1,  "minCount": 5 }
    ]
  }
}
```

含义：

- 最近 24 小时内同一角色同一文本出现 ≥ 10 次 → 记为高频。
- 最近 1 小时内同一角色同一文本出现 ≥ 5 次 → 记为高频。

每条规则独立扫描、独立入库；同一文本可能同时满足多条规则，则按 `(role_key, model_key, speech_hash, window_hours, min_count)` 区分。

### 3.2 数据存储模型

新增高频弹幕表（建议命名 `hot_danmaku`）：

```sql
CREATE TABLE hot_danmaku (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  role_key          TEXT NOT NULL,
  role_comment      TEXT,                   -- config.roles[role_key].comment，用于目录分类
  model_key         TEXT NOT NULL DEFAULT '',
  speech_text       TEXT NOT NULL,
  speech_hash       TEXT NOT NULL,          -- sha1(speech_text)
  window_hours      INTEGER NOT NULL,
  min_count         INTEGER NOT NULL,
  occurrences       INTEGER NOT NULL,
  first_seen_at_ms  INTEGER NOT NULL,
  last_seen_at_ms   INTEGER NOT NULL,
  status            TEXT NOT NULL DEFAULT 'pending'
                    CHECK (status IN ('pending','generating','ready','error')),
  audio_path        TEXT,                   -- 初始为 NULL/空，生成后写入
  error             TEXT,
  created_at_ms     INTEGER NOT NULL,
  updated_at_ms     INTEGER NOT NULL,
  metadata_json     TEXT NOT NULL DEFAULT '{}',
  UNIQUE (role_key, model_key, speech_hash, window_hours, min_count)
);

CREATE INDEX idx_hot_danmaku_time
  ON hot_danmaku(last_seen_at_ms DESC);

CREATE INDEX idx_hot_danmaku_status
  ON hot_danmaku(status);
```

说明：

- `audio_path` 允许为空，表示尚未生成音频。
- `status`：`pending`（待生成）、`generating`（生成中）、`ready`（已生成）、`error`（失败）。
- `model_key` 用于区分同一角色更换模型后的音频，避免旧音色被当作新结果。
- 只存满足高频条件的内容，不存全部弹幕。

### 3.3 检测流程

1. 按每条规则计算时间窗口：`windowStartMs = now - windowHours * 3600_000`。
2. 从 `danmaku` 表统计：

```sql
SELECT
  role_key,
  MAX(role_comment) AS role_comment,
  speech_text,
  speech_hash,
  COUNT(*) AS occurrences,
  MIN(received_at_ms) AS first_seen_at_ms,
  MAX(received_at_ms) AS last_seen_at_ms
FROM danmaku
WHERE received_at_ms >= :windowStartMs
  AND accepted = 1
  AND text_len BETWEEN :minLen AND :maxLen
GROUP BY role_key, speech_hash
HAVING COUNT(*) >= :minCount
ORDER BY occurrences DESC, last_seen_at_ms DESC
LIMIT :topN;
```

3. 对每条结果，结合当前角色配置得到 `model_key`。
4. 使用 `INSERT ... ON CONFLICT(...) DO UPDATE` 写入/更新 `hot_danmaku`：
   - 已存在且 `audio_path` 非空 → 保留音频，仅更新次数/时间。
   - 已存在但 `audio_path` 为空 → 保持 `pending`，更新统计。
   - 不存在 → 新增 `pending` 记录，`audio_path = NULL`。

### 3.4 生成/重新生成流程

1. WebUI 对某行点击“生成”或“重新生成”。
2. 后端接口 `POST /db/hot-danmaku/:id/generate`：
   - 将记录状态置为 `generating`。
   - 调用 TTS 合成接口（建议走低优先级队列）。
   - 成功后：
     - 写入音频文件到 `data/hot-danmaku/...`。
     - 更新 `audio_path`、`status='ready'`、`updated_at_ms`。
   - 失败后：
     - 保留原音频（如有），`status='error'`，记录 `error`。
3. “重新生成”与“生成”共用同一接口；若已有旧文件，可选择先删除或直接覆盖。
4. 生成期间前端轮询状态或等待接口返回，按钮显示“生成中”。

### 3.5 运行时命中（核心）

中间件每次收到弹幕后，除了正常清洗/入库，还要查询高频弹幕表：

1. 按当前弹幕的 `role_key + model_key + speech_text` 在 `hot_danmaku` 中查找。
2. 如果找到记录且 `audio_path` 非空、文件存在：
   - 直接播放该音频，不再请求 GPT-SoVITS。
   - `danmaku.tts_status = 'disk_cache_hit'`，`used_cache = 1`。
3. 如果未找到、`audio_path` 为空或文件丢失：
   - 回退到正常实时 TTS 合成。
   - 文件丢失时可把该高频记录标记为 `pending` 或 `error`，方便 WebUI 重新生成。

## 4. 音频地址方案（已确认：混合）

已选择 **方案 C（混合）**：目录使用中间件配置里的角色显示名（`role_comment`）做分类，文件名使用 hash。

格式：

```
data/hot-danmaku/<role_comment>/<speech_hash>.wav
```

例如：

```
data/hot-danmaku/樱羽艾玛/3f9a2c...wav
data/hot-danmaku/二阶堂希罗/8d1e7f...wav
```

说明：

- `role_comment` 来自 `config.roles[role_key].comment`，由中间件配置控制，不是用户弹幕内容，可读性好。
- 实现时建议对 `role_comment` 做基础清洗（去掉路径分隔符/非法字符）；如果 `comment` 为空，则回退到 `role_key`。
- 文件名用 `speech_hash = sha1(speech_text)`，固定长度、无非法字符、无路径穿越风险。
- 数据库 `audio_path` 保存**相对项目根目录**的路径，例如 `data/hot-danmaku/樱羽艾玛/xxx.wav`；读取时基于项目根目录解析，项目整体移动后依然有效。
- 重新生成时写临时文件后原子 rename 到同一路径，避免出现半截文件。

## 5. API 设计

### 5.1 高频弹幕列表

```
GET /db/hot-danmaku?role=&status=&text=&windowHours=&minCount=&limit=&offset=
```

返回 `hot_danmaku` 记录列表与总数。

### 5.2 手动触发扫描

```
POST /db/hot-danmaku/scan
```

按当前配置重新扫描 `danmaku`，更新高频弹幕表。可加 `X-DB-Token` 保护。

### 5.3 生成/重新生成

```
POST /db/hot-danmaku/:id/generate
```

合成该条音频并回填 `audio_path`。重复调用即重新生成。

### 5.4 试听音频

```
GET /db/hot-danmaku/:id/audio
```

返回音频文件流，供 WebUI 的 `<audio>` 和波形图使用。

> 写操作接口需要鉴权：建议至少要求 `database.readToken`（可改名为 `accessToken`），避免本机其他进程误触发。

## 6. WebUI 设计

### 6.1 高频弹幕页

页面以“高频弹幕卡片列表”展示，每个卡片对应一条高频弹幕，结构如下：

```
------------------------------------------------------------
| 这里是弹幕内容                                            |
| 地址：data/hot-danmaku/樱羽艾玛/3f9a2c....wav             |
| [波形图 Canvas]                                           |
| 音频时长：00:03.21    [播放]    [重新生成]                |
------------------------------------------------------------
```

- 顶部：手动扫描按钮、规则参数展示/筛选（角色、状态、文本、规则）。
- 每个卡片包含：
  - 弹幕内容
  - 角色显示名（`role_comment`）
  - 音频地址（相对路径）
  - 波形图
  - 音频时长
  - 播放按钮
  - 重新生成按钮
- 状态标签：
  - `pending`：灰色
  - `generating`：蓝色/动画
  - `ready`：绿色
  - `error`：红色
- 未生成时（`audio_path` 为空）：
  - 地址显示“未生成”
  - 波形图区域显示空状态
  - 按钮显示“生成”，而不是“重新生成”

### 6.2 试听与波形

- 每个卡片内直接内嵌简易播放器 + 波形图，不需要额外弹窗。
- 播放器：使用原生 `<audio controls>` 或自定义播放按钮 + `<audio>` 元素。
- 波形图：使用 Canvas 绘制。
- 波形实现思路（不依赖外部库）：
  1. `fetch('/db/hot-danmaku/:id/audio')` 获取 `ArrayBuffer`。
  2. 用 `AudioContext.decodeAudioData()` 解码。
  3. 取左右声道峰值，按画布宽度降采样绘制波形。
  4. 解码后同时得到音频时长，显示在卡片上。
  5. 如果解码失败，则只显示播放器，不阻塞试听。
- 每个卡片都有独立“重新生成”按钮；重新生成后刷新该卡片并重绘波形。

## 7. 配置设计

```jsonc
{
  "hotPhrase": {
    "enabled": true,
    "rules": [
      { "windowHours": 24, "minCount": 10 },
      { "windowHours": 1,  "minCount": 5 }
    ],
    "topN": 100,
    "minTextLength": 2,
    "maxTextLength": 80,
    "maxGeneratePerRound": 5,
    "skipWhileBusy": true,
    "scanIntervalMs": 60000,
    "audioDir": "data/hot-danmaku"
  }
}
```

说明：

- `rules` 支持多条高频判定规则。
- `audioDir` 是音频文件根目录；数据库保存相对项目根目录的路径，例如 `data/hot-danmaku/<role_comment>/<speech_hash>.wav`（已确认混合方案）。
- `scanIntervalMs` 控制自动扫描周期；也可以只在 WebUI 手动扫描。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 音频地址后续调整 | 需要迁移文件/数据库路径 | 已确认混合方案；DB 存相对路径，迁移时只需批量更新 `audio_path` 并移动文件 |
| 文件名非法/路径穿越 | 生成失败或安全问题 | 避免直接拼接弹幕文本；优先 hash 或清洗 |
| 生成任务长时间占用 TTS | 实时弹幕延迟 | 低优先级队列、`skipWhileBusy`、单轮限量 |
| 音频文件丢失 | 试听/播放失败 | 读取前校验文件存在；丢失则状态置为 pending 并允许重新生成 |
| WebUI 写操作被误触发 | 意外消耗 GPU | 写接口加 Token 鉴权；按钮二次确认 |

## 10. 已确认与待确认事项

已确认：

1. **音频地址方案**：混合方案 C——目录用中间件配置的角色显示名（`role_comment`），文件名用 `speech_hash`。
2. **高频弹幕列表**：`hot_danmaku` 表保存高频弹幕内容 + 音频地址，`audio_path` 初始为空。
3. **运行时命中**：中间件每次收到弹幕都查询高频弹幕表，匹配到已生成音频则直接播放。
4. **WebUI 卡片**：每条高频弹幕显示内容、地址、波形图、音频时长、播放按钮、重新生成按钮。

待确认：

- 是否还需要保留 `tts_audio_cache` 作为通用运行时缓存表，还是只由高频弹幕表承担命中。
- 高频判定使用多条规则并存，还是只保留一组 `windowHours + minCount`。

> 以上两点不影响当前主体设计；实现前可以再定。
